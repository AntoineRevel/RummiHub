# Solver performance comparator

A self-contained benchmark for the Rummikub solvers. It answers one question objectively:
**how do DynamicSolver and the graph fallback compare on performance?** Time, memory and CPU
are measured, and each move is checked for legality and for divergence from the
dynamic-programming baseline.

Everything runs in memory. There is no Redis, SignalR or Aspire dependency, and no external
NuGet package was added.

## How it works

1. A reproducible **game trace** is generated by a light game loop (`RummiHub.SolverBench.Trace`)
   piloted by `DynamicSolver`: it plays a seeded game and captures every real position
   (board + hand + `hasPlayed`), tagged by phase.
2. Each captured position is solved by **every selected solver** (first-play solvers get
   first-play positions, during-game solvers get during-game positions). Each receives a *copy*
   of the sets.
3. For every `(position, solver)` the harness measures, sequentially and with a warmup:
   - **Time** — high-resolution `Stopwatch`, median + p95 over N repetitions.
   - **Allocations** — `GC.GetTotalAllocatedBytes(precise)` delta (captures parallel threads).
   - **GC** — `GC.CollectionCount(0/1/2)` deltas.
   - **CPU** — `Process.TotalProcessorTime` delta, plus the CPU/wall ratio (a parallelism factor).
   - A per-solve **timeout** via `CancellationTokenSource`, recorded as `TIMEOUT` (never blocks).
4. Every result is checked for **legality** independently with
   `RummiHub.Solver.Worker.Solver.Dynamic.SolutionValidator`, and compared to the
   **DynamicSolver baseline**: during-game on rack-tiles-played, first-play on existence
   (the first-play solvers satisfice rather than maximize score). Divergences and illegal or
   over-scored moves are surfaced as potential bugs — no solver is treated as absolute truth.

> Measurements are **indicative**, not BenchmarkDotNet-grade. They are taken sequentially with a
> clean GC between solvers, a warmup, and median/p95 reporting. Use a Release build for the most
> meaningful numbers, and always note the seed.

### Picking the best solver

The results are ranked **per phase** and the winner is highlighted (🏆 / 🥇). Ranking by raw median
time alone would be misleading — a solver that times out on the hard positions looks "fast" because
only its easy solves count toward the median. So a solver must first be **qualified** (complete and
correct over the corpus: no timeout, no illegal move, no divergence from the baseline), and only
then is it ranked by speed and memory. The best solver is the fastest qualified one.

## Move bank

`solver-bench/bank/` holds one JSON file per position (`RummiJsonOptions.Default`), usable as a
benchmark / non-regression corpus (same positions ⇒ same verdicts). Entries are enriched:

- **manually** from the `/bench` page (paste an opening hand, or curate a position from a run);
- **automatically** by heuristics — high tile count, big board rearrangement, repositioned
  jokers, slow solves or wide performance gaps.

## Running it

### Web UI

Browse to **`/bench`**: pick solvers, choose a corpus (seeded trace or the bank), set repetitions
and timeout, run, and read the sortable detail table plus the per-solver summary. Illegal and
divergent rows are highlighted.

### Headless runner (CI / scripting)

```bash
# Compare all solvers on a seeded trace and export reports
dotnet run --project RummiHub.SolverBench.Runner -c Release -- \
    --seed 12345 --reps 5 --timeout-ms 2000 --csv out.csv --md out.md

dotnet run --project RummiHub.SolverBench.Runner -- --list-solvers
dotnet run --project RummiHub.SolverBench.Runner -- --source bank --phase during
dotnet run --project RummiHub.SolverBench.Runner -- --seed-bank 10   # seed the bank from a trace
```

The runner is deterministic in its verdicts (found / legal / optimum), so it reaches the same
conclusions as the UI. Exit code `2` means a solver produced an illegal move.
